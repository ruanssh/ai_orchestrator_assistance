Como funciona a IA do SQMS

Um guia visual de ponta a ponta: da pergunta digitada no widget do assistente até a resposta fundamentada em procedimentos corporativos e em dados reais do SQMS. Inclui o que é RAG, o que é BM25, o que é reranking — e, principalmente, o que está de fato ligado hoje.

Resumo em uma frase

A IA do SQMS combina um LLM com recuperação de documentos corporativos, usando BM25 como busca lexical ativa, enquanto embeddings e reranking existem como recursos opcionais desabilitados por padrão.

Visão geral da arquitetura

Seis blocos, dois caminhos possíveis. O usuário nunca fala direto com o LLM: tudo passa pelo backend do SQMS, que autentica, revalida permissões e decide qual fluxo atende a pergunta.

Componente ativo — em uso hoje, na configuração padrão.
Componente opcional — existe no código, desligado por padrão.
Dados reais do SQMS — solicitações, prazos e status do banco.
Chamada ao LLM — geração de texto pelo modelo.
Fluxo de ida — a pergunta descendo pelas camadas.
Fluxo de resposta — o retorno até a tela do usuário.
Ponte entre os fluxos — o agente também consulta os procedimentos.

A requisição
POST /app/ai-assistant/chat
{ "message": "...", "session_id": "uuid", "flow_id": "procurement",
  "page_context": { "screen": "approval.list", "filters": {...}, "page": 1, "size": 10 } }

  • DELETE /app/ai-assistant/sessions/{id} limpa a conversa.

A decisão de rota, no código
if body.page_context is not None and ai_assistant_agent_enabled():
    → AssistantAgent  (Fluxo B, dentro do sqms-back)
else:
    → AiAssistantClient.chat()  →  POST /api/v1/chat  (Fluxo A, orquestrador)

ai_assistant_agent_enabled() lê a variável AI_ASSISTANT_AGENT_ENABLED (1 no .env, 0 no .env.dev). O orquestrador roda em FastAPI na porta 8200, apontado por AI_ORCHESTRATOR_URL.

Onde entra o LLM: nunca no navegador. A primeira chamada ao modelo acontece já dentro do backend (Fluxo B) ou dentro do orquestrador (Fluxo A) — depois da autenticação e da revalidação de permissão.

Onde entra o BM25: só dentro do orquestrador. No Fluxo A ele roda sempre; no Fluxo B ele só roda se o modelo decidir chamar a ferramenta search_procedures.

As camadas, uma a uma

Cada camada tem uma responsabilidade única e não confia na camada anterior mais do que precisa. Esse é o princípio que sustenta a segurança do assistente.

1 · Usuário

Quem pergunta

Interage com o widget “Assistente SQMS” dentro do próprio sistema. Escreve em português, sem precisar saber nada de tela, de filtro ou de procedimento.

2 · Frontend SQMS

Envia pergunta e contexto

  • Envia a pergunta digitada.
  • Pode enviar o contexto da tela atual: lista de solicitações, detalhe de uma solicitação ou dashboard.
  • Mantém o identificador público da sessão, para a conversa ter continuidade.
3 · Backend SQMS

Autentica, revalida e reconstrói

  • Autentica o usuário da requisição.
  • Converte o identificador público em uma sessão interna vinculada ao usuário, para conversas não vazarem entre pessoas.
  • Revalida permissões a cada pergunta.
  • Reconstrói o contexto da tela usando os controllers reais do SQMS — os mesmos que a tela usa.
  • Encaminha a pergunta ao assistente/orquestrador.
  • Expõe apenas ferramentas somente leitura.
4 · Provedor LLM

Quem escreve a resposta

O modelo de linguagem gera o texto final. Ele nunca recebe credenciais do usuário nem acesso ao banco: recebe apenas o material que as camadas anteriores já filtraram e autorizaram.

Por que reconstruir o contexto no servidor? Porque o que o navegador envia é apenas um descritor (“tela de lista, filtro X, página 2”). O backend refaz a consulta com a permissão real do usuário. Um uid forjado no cliente não vira acesso: o mesmo controller que protege a tela recusa o documento.

Como o snapshot da tela é montado

build_page_snapshot() chama os mesmos controllers da tela — DocumentFlowController.get_all_documents, get_document_by_id e DashboardDocumentsController — e depois:

  • remove qualquer chave que contenha url, path, mime_type, base64 ou signature;
  • calcula days_to_deadline e overdue em Python — a conta de prazo nunca é deixada para o modelo;
  • ordena por urgência e corta o snapshot em 6.000 caracteres, marcando truncated: true quando precisa cortar.

Dois fluxos possíveis

O backend escolhe o caminho conforme a pergunta e o contexto disponível. São dois modos de responder, com fontes de verdade diferentes.

Fluxo A

RAG / Orquestrador

“Qual é a regra para aprovar uma compra de R$ 6.000?”

  • Usado para perguntas sobre procedimentos, regras, cotações, aprovações e equipamentos.
  • Consulta a base de documentos Markdown.
  • Retorna a resposta com as fontes consultadas.
Fluxo B

Agente consciente da tela

“Dessas solicitações, qual é a mais urgente?”

  • Usado quando o contexto da tela está disponível e o agente está habilitado.
  • Consulta dados reais do SQMS.
  • Pode usar as ferramentas get_request_detail, search_requests e search_procedures.
  • É somente leitura.

Limite absoluto: o assistente nunca aprova, rejeita, cria ou altera uma solicitação. Ele lê, explica e orienta. Qualquer ação continua sendo feita pela pessoa, pela tela do SQMS.

As três ferramentas do Fluxo B

get_request_detail

Busca os detalhes completos de uma solicitação pelo seu uid: assunto, tipo, status, itens e prazo.

search_requests

Busca solicitações visíveis para o usuário atual por assunto, status ou tipo, quando a pergunta escapa da tela.

search_procedures

Consulta a base de procedimentos — é a ponte do agente com o Fluxo A, para perguntas de “qual é a regra”.

▸ Ver a regra de roteamento e o laço de ferramentasquantas vezes o LLM é chamado
A regra, sem ambiguidade

Não é o assunto da pergunta que escolhe o fluxo — é o que o frontend enviou. Se veio contexto de tela e o agente está ligado, quem responde é o Fluxo B; caso contrário, o Fluxo A. Por isso a mesma pergunta pode ser atendida por caminhos diferentes conforme a tela em que a pessoa está.

  • Telas que registram contexto hoje: lista de aprovações, detalhe de uma solicitação e dashboard.
  • Em qualquer outra tela, não há contexto — e a pergunta segue pelo Fluxo A.
O laço de tool calling do Fluxo B
MAX_TOOL_ROUNDS   = 3     # no máximo 3 chamadas ao LLM por pergunta
MAX_HISTORY_MESSAGES = 8  # histórico enviado ao modelo
MAX_OUTPUT_TOKENS = 1200  # teto da resposta
  • Rodada 1 e 2: o modelo recebe as ferramentas e pode pedir dados.
  • Rodada 3: as ferramentas são enviadas vazias de propósito, forçando uma resposta definitiva — o laço nunca fica preso.
  • Cada retorno de ferramenta volta ao modelo como mensagem role: "tool", no formato OpenAI.
Por que as ferramentas são seguras

O ToolContext carrega user_id e business_id vindos do request autenticado, nunca dos argumentos que o modelo inventa. Se o modelo pedir um uid que a pessoa não pode ver, é o próprio controller do SQMS que recusa (SQMSForbiddenException) e a ferramenta devolve {"error": ...} — sem vazar nada.

Onde entra o LLM: de 1 a 3 chamadas por pergunta no Fluxo B, todas com o catálogo de ferramentas anexado.

O que é RAG

RAG é a sigla de Retrieval-Augmented Generation, em português “Geração Aumentada por Recuperação”. A ideia é simples: em vez de confiar na memória do modelo, primeiro recuperamos os trechos certos dos documentos da empresa e só então pedimos ao modelo que gere a resposta usando aqueles trechos como base.

▸ Ver as três chamadas ao LLM do Fluxo Aplanejar · selecionar · responder

Uma pergunta no Fluxo A gera três chamadas distintas ao modelo, com papéis diferentes:

  • 1. Planejar — _plan(), temperatura 0.0. Devolve JSON: {"queries": [...], "topics": [...], "needs_knowledge": true}. Cria até 3 consultas curtas e independentes. Saudação e conversa casual saem daqui com needs_knowledge: false e o RAG nem é acionado.
  • 2. Selecionar — _select_evidence(), temperatura 0.0. Devolve {"selected_ids": [...], "additional_queries": [...], "ready": true}.
  • 3. Responder — _answer(), temperatura 0.25. É a única chamada que produz o texto que a pessoa lê.

Onde entra o BM25: exatamente entre a chamada 1 e a chamada 2. O LLM escreve as consultas, o BM25 as executa sobre a base Markdown, e o LLM volta para escolher o que serve.

O ciclo pode repetir

Se a seleção responder ready: false e sugerir novas consultas, o orquestrador busca de novo — limitado por max_search_iterations: 2. É o que permite responder perguntas com dois assuntos, como “como faço a cotação e quem aprova esse valor”.

Base de conhecimento

A base é um conjunto de arquivos Markdown mantidos pela empresa. Não há banco vetorial externo nem serviço de terceiros: os arquivos ficam na pasta procedures_rag e são indexados na subida.

RAG_SQMS_CAMPOS.md

Os campos do SQMS e o que cada um significa no preenchimento de uma solicitação.

RAG_COTAÇÃO_COMPRAS.md

O procedimento de cotação e compras: passos, papéis, validações e aprovações.

RAG_BASELINE_NOTEBOOK_COMPUTADOR.md

O baseline de equipamentos de TI: notebooks e computadores, configurações e critérios.

Como um documento vira trechos buscáveis

Cada arquivo é dividido em seções pelos títulos do Markdown, preservando a hierarquia (título, subtítulo, sub-subtítulo). Cada seção vira uma unidade independente de busca, com estes campos:

  • IDIdentificador único da seção.
  • DocumentoO arquivo de origem.
  • TítuloO título do documento.
  • Caminho da seçãoA trilha de títulos até ela.
  • Linhas de origemLinha inicial e final no arquivo.
  • ConteúdoO texto da seção em si.

É por causa desses campos que a resposta consegue vir com fontes: o sistema sabe exatamente de qual documento, de qual seção e de quais linhas cada afirmação saiu.

▸ Ver como o Markdown vira índiceparser, campos e reindexação
A indexação

Na subida, KnowledgeBase.reindex() varre **/*.md em cada knowledge_paths do fluxo — no fluxo procurement, a pasta ../procedures_rag — e passa cada arquivo pelo MarkdownSectionParser. Dá para reindexar sem reiniciar com POST /api/v1/knowledge/reindex.

Os dois textos de cada seção
  • search_text = título do documento + trilha de seções + metadados + conteúdo. É esse texto que o BM25 indexa — por isso um termo que aparece só no título da seção também é encontrável.
  • citation_text = bloco [EVIDENCE <id>] com documento, seção e linhas. É esse texto que vai para o LLM, e é dele que saem as fontes da resposta.
Hierarquia preservada

Cada seção guarda parent_id, level e heading_path. É isso que depois permite a expansão pai/filhos/próxima seção na etapa de evidências — sem hierarquia, o trecho chegaria ao modelo fora de contexto.

O pipeline de recuperação

Aqui está a parte que mais gera confusão. São quatro peças, e só uma delas está ligada hoje. O diagrama abaixo mostra o caminho real: contínuo para o que está ativo, tracejado para o que existe no código mas está desabilitado por padrão.

▸ Ver os parâmetros do pipelinenenhum LLM roda nesta etapa
O método, na íntegra conceitual
lexical  = BM25.search(query, 15)          # lexical_candidates = 15
semantic = Semantic.search(query, 15)     # semantic_candidates = 15  (vazio hoje)
candidates = RRF([lexical, semantic], 16) # max(final_candidates * 2, 12)
return Reranker.rerank(query, candidates, 8)  # final_candidates = 8
  • Antes da fusão, os resultados são filtrados por fluxo: só entram seções que pertencem ao flow_id da pergunta.
  • Com a busca semântica desligada, semantic é sempre uma lista vazia — o RRF recebe um ranking só.
  • Com o reranking desligado, rerank() devolve results[:limit], ou seja, apenas corta a lista.

Onde entra o LLM: em lugar nenhum. Esta etapa é 100% algorítmica e determinística — o modelo só aparece antes (escrevendo as consultas) e depois (selecionando e respondendo).

BM25 — a busca que está ligada

BM25 é um algoritmo de recuperação lexical: ele trabalha com palavras e com a frequência em que elas aparecem. É a peça que hoje encontra os trechos certos nos documentos da Salcomp.

BM25: ativo por padrão bm25s bm25s.BM25 Busca lexical, não generativa

Como ele decide o que é relevante

  • Compara os termos da pergunta com os termos dos documentos Se você pergunta por “cotação”, ele procura seções que contenham essa palavra.
  • Considera a frequência das palavras Uma seção que fala de “cotação” várias vezes provavelmente é mais sobre cotação do que uma que cita a palavra de passagem.
  • Considera a relevância do termo no conjunto Palavras raras pesam mais. “Baseline” diz muito mais sobre o assunto do que “de” ou “para”.
  • Penaliza documentos muito longos Um texto enorme tende a conter qualquer palavra por acaso; o algoritmo corrige esse viés pelo tamanho.
  • É ótimo quando os termos batem Funciona muito bem quando a pessoa usa exatamente — ou quase — as mesmas palavras do procedimento.

Importante, para não haver confusão: BM25 não é inteligência artificial generativa. É um algoritmo de busca lexical, matemático e determinístico, criado décadas antes dos LLMs. Ele não escreve nada — apenas encontra e ordena trechos. Quem escreve a resposta é o LLM, depois.

▸ Ver a implementação do BM25bm25s, stopwords em português
Indexação
tokens = bm25s.tokenize([s.search_text for s in sections], stopwords="pt")
retriever = bm25s.BM25(corpus=corpus)
retriever.index(tokens, show_progress=False)
Consulta
query_tokens   = bm25s.tokenize([query], stopwords="pt")
results, scores = retriever.retrieve(query_tokens, k=min(limit, len(sections)))
# resultados com score <= 0 são descartados
  • Stopwords em português (stopwords="pt"): “de”, “para”, “o”, “a” são removidos antes de pontuar — é isso que impede que palavras vazias dominem o ranking.
  • O índice vive em memória, reconstruído na subida do serviço ou no reindex. Não há banco de busca externo.
  • Não exige GPU nem download de modelo: é matemática sobre contagem de palavras.

Resumindo o papel dele: o BM25 é a única peça de recuperação que roda hoje. Se ele não encontrar a seção certa, nenhuma etapa posterior conserta — o LLM só vê o que o BM25 trouxe.

Busca semântica por embeddings

Componente opcional. Complementa o BM25 nos casos em que a pessoa descreve a situação com palavras totalmente diferentes das que estão escritas no procedimento.

Busca semântica: desabilitada por padrão sentence-transformers BAAI/bge-m3 SQMS_AI_SEMANTIC_ENABLED=true

O que ela faz

  • Converte perguntas e documentos em vetores.
  • Encontra textos semanticamente parecidos mesmo quando as palavras são diferentes.
  • Usa a biblioteca sentence-transformers.
  • O modelo configurado é BAAI/bge-m3.

Status real hoje

Está desabilitada por padrão. Só é ativada quando SQMS_AI_SEMANTIC_ENABLED=true.

Na prática: hoje o sistema não gera embeddings e não faz busca por similaridade de significado. O código está pronto, mas o caminho não é executado.

▸ Ver a implementação dos embeddingspor que ela não roda hoje 
model = SentenceTransformer("BAAI/bge-m3")
embeddings = model.encode(textos, normalize_embeddings=True)
scores = embeddings @ query_embedding      # produto escalar = similaridade
  • Como os vetores são normalizados, o produto escalar equivale à similaridade de cosseno.
  • Depende do extra opcional: pip install -e ".[semantic]". Sem ele, ligar a flag levanta RuntimeError pedindo a instalação.
  • Com enabled=False, tanto index() quanto search() retornam imediatamente — nenhum modelo é baixado e nenhum vetor é calculado.
Para ligar
SQMS_AI_SEMANTIC_ENABLED=true
SQMS_AI_EMBEDDING_MODEL=BAAI/bge-m3

Custo a considerar antes de ligar: a indexação passa a rodar um modelo sobre todas as seções na subida, o que exige memória e tempo — e, sem GPU, deixa o start bem mais lento.

RRF — Reciprocal Rank Fusion

Peça intermediária e complementar: ela existe para juntar os resultados de mecanismos de busca diferentes numa única lista ordenada.

O que o RRF combina

  • O ranking do BM25 (busca lexical).
  • O ranking da busca semântica por embeddings.

Ele não soma notas — que seriam incomparáveis entre si. Ele olha a posição de cada trecho em cada lista: quem aparece bem colocado em mais de um mecanismo sobe na lista final.

O que acontece no estado atual

Como a busca semântica está desabilitada, o RRF recebe apenas um ranking, o do BM25.

Ou seja: a fusão continua no caminho, mas o ranking efetivo vem principalmente do BM25. O RRF só passa a fazer diferença de verdade quando um segundo mecanismo for ligado.

RRF: disponível para combinar rankings Hoje recebe só o ranking do BM25
▸ Ver a fórmula do RRFpor que soma posição, não nota 
for lista in [lexical, semantic]:
    for rank, item in enumerate(lista, start=1):
        score[item.id] += 1 / (60 + rank)     # k = 60
  • O 1º colocado soma 1/61 ≈ 0,0164; o 10º soma 1/70 ≈ 0,0143. A diferença é pequena de propósito: o RRF valoriza aparecer bem em várias listas mais do que liderar uma só.
  • Ele ignora a escala das notas — e isso é o ponto. A nota do BM25 e a similaridade de cosseno vivem em escalas incomparáveis; somá-las diretamente seria errado.
  • O k = 60 amortece o peso das primeiras posições, evitando que um único mecanismo domine a lista final.

Hoje, na prática: com uma lista só na entrada, a soma preserva a ordem que o BM25 já tinha. O RRF está no caminho, mas não muda nada — ele só passa a ter efeito quando um segundo mecanismo for ligado.

Reranking

Reranking é uma segunda etapa de ordenação. A primeira busca é rápida e ampla; o reranker é lento e criterioso, e reavalia os finalistas um a um.

  • A busca inicial recupera vários candidatos O objetivo aqui é abrangência: trazer tudo que pode ser relevante, sem se preocupar com a ordem exata.
  • Um modelo mais especializado reavalia cada par pergunta–trecho Diferente da busca, ele lê a pergunta e o trecho juntos e julga o quanto um responde ao outro.
  • Os resultados são reorganizados por relevância A lista final chega ao LLM com os melhores trechos no topo.
O projeto tem suporte a reranking sentence-transformers.CrossEncoder BAAI/bge-reranker-v2-m3 Reranking: desabilitado por padrão SQMS_AI_RERANK_ENABLED=true

Conclusão honesta: o sistema não está usando reranking em produção por padrão. A implementação existe e é a que está descrita acima, mas fica inativa enquanto a variável de ambiente não for ligada.

▸ Ver a implementação do rerankerCrossEncoder, carregado sob demanda 
model = CrossEncoder("BAAI/bge-reranker-v2-m3")     # carregado no 1º uso
scores = model.predict([(query, s.search_text) for s in results])
results = ordenar_por(scores)[:limit]
A diferença entre buscar e reranquear

A busca compara a pergunta com um índice — rápida, mas grosseira. O CrossEncoder lê a pergunta e o trecho juntos, no mesmo passe, e devolve o quanto um responde ao outro. É muito mais preciso e muito mais caro: por isso só se aplica aos finalistas, nunca à base inteira.

Com a flag desligada
if not self.enabled or not results:
    return results[:limit]        # passa direto, sem reordenar

Ou seja: hoje a ordem que chega ao LLM é a ordem do BM25. Para ligar: SQMS_AI_RERANK_ENABLED=true (também exige o extra semantic instalado, porque o CrossEncoder vem do sentence-transformers).

Seleção de evidências

Antes de escrever a resposta, há outra chamada ao LLM — dessa vez não para responder, mas para escolher. É o que separa “achou algo parecido” de “achou o que responde”.

Chamada ao LLM

O que essa etapa faz

  • Analisa os candidatos recuperados pelo pipeline de busca.
  • Seleciona as seções necessárias para responder — podem ser várias, complementares.
  • Pode solicitar novas consultas se perceber que faltou um assunto na pergunta.
Expansão

Trazendo o contexto ao redor

Um trecho isolado costuma perder o sentido. Por isso, depois de escolher as seções, o sistema expande as seções relacionadas:

  • a seção pai, para recuperar o enquadramento;
  • as seções filhas, para pegar os detalhes;
  • a seção seguinte, para não cortar o procedimento no meio.

Esse ciclo — buscar, selecionar, e se necessário buscar de novo — é o que dá ao assistente a chance de responder perguntas que misturam dois assuntos, como “como faço a cotação e quem aprova esse valor”.

▸ Ver o ciclo de decisão e o orçamento de contextoaté 2 rodadas de busca
O que o modelo recebe para decidir

Um catálogo com os 10 melhores candidatos, cada um cortado em 1.200 caracteres — o suficiente para julgar relevância sem gastar contexto à toa.

As saídas possíveis
  • ready: true → segue para a resposta com os selected_ids escolhidos.
  • ready: false + additional_queries → nova rodada de busca (limite: max_search_iterations = 2).
  • Se nada for selecionado, há um fallback: os 4 melhores candidatos entram assim mesmo.
Expansão

KnowledgeBase.expand() acrescenta, para cada seção escolhida: a seção pai, todas as seções filhas e a próxima seção irmã — e sempre checando se a seção pertence ao fluxo, para a expansão não vazar conteúdo de outra base.

Orçamento de contexto
max_evidence_tokens = 2100        # ≈ 8.400 caracteres (4 chars por token)
llm_context_tokens  = 4096

As evidências são empacotadas até esse limite; o que não couber fica de fora, e um último trecho pode entrar cortado se sobrarem mais de 500 caracteres de espaço.

Memória de conversa

Sem memória, cada pergunta começaria do zero. Com memória, a pessoa pode dizer “e para valores maiores?” e o assistente sabe do que ela está falando.

Como funciona

  • Memória de conversa por sessão — cada conversa tem seu próprio histórico.
  • Armazenada em um banco SQLite, o arquivo sessions.db.
  • Há um limite de mensagens armazenadas: as mais antigas são descartadas conforme a conversa avança.

Por que ela é segura

As sessões são vinculadas ao usuário pelo backend. O identificador que o navegador conhece é público; o backend o transforma em uma chave interna derivada do usuário autenticado.

Consequência prática: mesmo que alguém descubra o identificador de sessão de outra pessoa, não alcança a conversa dela.

▸ Ver as duas memórias do sistemaSQLite no orquestrador, store no backend
Memória do orquestrador (Fluxo A)
data/sessions.db  —  SQLite
messages(id, session_id, role, content, created_at)
max_history_messages = 8

A cada append, um DELETE apaga tudo que passar das 8 mensagens mais recentes daquela sessão — a tabela não cresce indefinidamente. O acesso é serializado por um lock, então requisições concorrentes não corrompem o arquivo.

Memória do agente (Fluxo B)

O agente usa o DraftSessionStore do próprio SQMS, com a chave assistant:<sessão interna> e as mesmas 8 mensagens. O store usa Redis quando REDIS_URL está configurado; hoje a variável está vazia no .env, então ele opera em memória do processo — o histórico se perde quando o backend reinicia.

O vínculo com o usuário
internal_session_id = sha256(f"{user_id}:{public_session_id}")

As duas memórias são indexadas por essa chave derivada. Descobrir o identificador público de outra pessoa não dá acesso à conversa dela, porque a chave real depende do usuário autenticado.

O provedor LLM

O modelo de linguagem é tratado como um serviço trocável. Nada na arquitetura depende de um fornecedor específico.

Como o modelo é acessado

  • API compatível com OpenAI — o padrão de mercado para chamadas de chat.
  • Endpoint /chat/completions.
  • Modelo configurável por ambiente, sem alteração de código.
  • Temperatura baixa, para respostas mais determinísticas e menos criativas.

Por que temperatura baixa

Em procedimento corporativo, criatividade é defeito. Faixas de valor, cargos, ordem de aprovação e exceções precisam sair exatamente como estão escritos na evidência — não numa versão “melhorada” pelo modelo.

▸ Ver qual modelo está em usogateway, endpoint, temperaturas e retentativas
O provedor

É um gateway interno compatível com OpenAI — a Lity, descrita no README do orquestrador como o provider inicial, sem acoplamento com o núcleo. Backend e orquestrador apontam para o mesmo gateway, por variáveis diferentes: 

# orquestrador          # backend
SQMS_AI_LLM_BASE_URL    LLM_BASE_URL     = http://10.64.10.48/v1
SQMS_AI_LLM_API_KEY     LLM_API_KEY
SQMS_AI_LLM_MODEL       LLM_MODEL        = auto
Qual modelo responde

O valor configurado é auto: quem escolhe o modelo real é o gateway, não a aplicação. O nome efetivo volta no campo model de cada resposta e é repassado até a tela — numa verificação direta ao gateway, auto foi resolvido para qwen35-122b. Trocar de modelo é trocar variável de ambiente; nenhuma linha de código muda.

Parâmetros por tipo de chamada
  • Resposta final (Fluxo A): temperature = 0.25.
  • Etapas de JSON (planejar e selecionar evidências): temperature = 0.0.
  • Agente (Fluxo B): max_tokens = 1200, com tool calling nativo no formato OpenAI.
  • Contexto: SQMS_AI_LLM_CONTEXT_TOKENS = 4096.
Resiliência

Timeout de 120 segundos e até 3 tentativas com espera crescente (0,5s → 1s → 2s) em falha de conexão ou nos status 429, 500, 502, 503 e 504. Se ainda assim falhar, o erro sobe como 502 para o frontend, que mostra o botão de tentar de novo.

A resposta final

Na última chamada, o modelo recebe tudo o que as camadas anteriores prepararam — e devolve um pacote completo, não só um texto.

Entra

O que o LLM recebe

  • A pergunta atual.
  • O histórico recente da conversa.
  • As evidências recuperadas da base de procedimentos.
  • O contexto do SQMS, quando aplicável — o snapshot da tela e os dados reais.
Sai

O que volta para a tela

  • A resposta em português.
  • As fontes consultadas: documento, seção e linhas.
  • O ID da sessão, para a conversa continuar.
  • O modelo utilizado na geração.
▸ Ver o formato da respostao payload que chega na tela 
{
  "answer":     "texto em português",
  "session_id": "uuid público",
  "flow_id":    "procurement",
  "model":      "modelo que respondeu",
  "sources":    [ { "id", "document", "title", "section", "lines", "score" } ],
  "debug":      null
}
  • Os dois fluxos devolvem o mesmo formato — o frontend não precisa saber por onde a pergunta passou. No Fluxo B, sources vem vazio, porque a resposta veio de dados do SQMS e não de seções de documento.
  • lines é o intervalo de linhas no arquivo Markdown original: dá para abrir o documento e conferir a frase exata que embasou a resposta.
  • debug só é preenchido quando SQMS_AI_DEBUG_RESPONSES=true, e traz o plano, as consultas executadas e os IDs candidatos e selecionados — é a ferramenta para entender por que uma resposta saiu como saiu.
Registro de uso

Cada resposta do Fluxo B registra uso de IA em segundo plano (usuário, operação, modelo, tokens, latência e status), sem bloquear a resposta. A operação é nomeada por tela — por exemplo chat:approval.list+1tool — o que permite saber depois quais telas realmente usam o assistente e quantas rodadas de ferramenta foram necessárias.
